# Техническое задание: Trello Team Analytics

**Версия:** 1.0  
**Тип проекта:** внутреннее веб-приложение для аналитики командной разработки  
**Основная цель:** собирать историю работы команды из Trello, рассчитывать метрики доставки задач и качества, предоставлять тимлиду аналитику за выбранные периоды и формировать регулярные обзоры выполненной работы.

---

# 1. Цели и задачи проекта

## 1.1. Цель

Разработать веб-приложение, которое интегрируется с одной доской Trello, сохраняет историю изменений карточек и предоставляет объективную картину работы команды на основе фактических событий.

Приложение должно помогать отвечать на вопросы:

- Какие задачи команда закрывает и сколько их?
- Как меняется скорость доставки задач со временем?
- Сколько времени проходит от начала работы над задачей до её завершения?
- Какие задачи выполняются слишком долго?
- Как часто исправленные баги возвращаются в работу?
- Сколько времени требуется на исправление возвращённых багов?
- Кто над какими задачами работал и как распределена нагрузка?
- Какие задачи были выполнены за день или за последние несколько дней?
- Какие задачи остаются незавершёнными и где возникают задержки?
- Какие изменения произошли по сравнению с предыдущим периодом?

Приложение предназначено для анализа процессов и улучшения командной работы, а не только для подсчёта количества закрытых карточек.

## 1.2. Основные пользователи

**Тимлид:**
- анализирует скорость доставки и динамику работы команды;
- изучает проблемные задачи;
- отслеживает возвраты багов и время повторного исправления;
- формирует обзоры для дейликов и встреч;
- анализирует историю за произвольные периоды.

**Разработчики и другие участники команды:**
- просматривают общую статистику;
- изучают собственные задачи и их историю;
- видят текущую работу команды;
- используют отчёты для подготовки к дейликам.

**Администратор:**
- управляет доступом пользователей;
- настраивает интеграцию с Trello;
- запускает синхронизацию;
- контролирует состояние импорта и системы.

## 1.3. Основные ограничения

- Подключается одна доска Trello.
- Исторические данные должны импортироваться настолько полно, насколько это позволяет API Trello.
- Приложение доступно нескольким пользователям одновременно.
- Локальная разработка выполняется в Docker Compose.
- Production-развёртывание осуществляется на существующем сервере с Nginx, без обязательного использования Docker.
- Backend — Go.
- Frontend — Vue 3 и TypeScript.
- Основная БД — PostgreSQL.
- Разработка ведётся через Cursor с использованием ИИ-агентов, правил, навыков и команд.

# 2. Технологический стек

## 2.1. Backend

- Go — основной язык приложения.
- REST API — взаимодействие frontend и backend.
- PostgreSQL — хранение карточек, истории изменений, пользователей, настроек и агрегированных данных.
- Механизм фоновой синхронизации Trello.
- Миграции схемы базы данных.
- Структурированное логирование.
- Unit- и integration-тесты.

## 2.2. Frontend

- Vue 3.
- TypeScript.
- Composition API.
- Vue Router.
- Библиотека графиков для отображения метрик.
- Адаптивный интерфейс для настольных компьютеров и планшетов.
- Единый HTTP-клиент для работы с REST API.
- Централизованная обработка ошибок API.

Выбор дополнительных библиотек необходимо зафиксировать в проектной документации до начала реализации соответствующего функционала.

## 2.3. Инфраструктура

**Локальная среда:**
- Docker Compose.
- PostgreSQL в контейнере с постоянным volume.
- Go backend.
- Vue dev server.
- Конфигурация через `.env`.

**Production:**
- Nginx раздаёт собранный frontend и проксирует запросы к API.
- Go backend запускается как сервис `systemd`.
- PostgreSQL работает на сервере или использует существующий доступный экземпляр.
- Конфигурация production хранится отдельно от исходного кода.
- Docker Compose не является обязательным инструментом production-развёртывания.

# 3. Интеграция с Trello

## 3.1. Подключение

Реализовать подключение к одной выбранной доске Trello.

Приложение должно получать и сохранять:

- идентификатор и название доски;
- списки доски;
- карточки;
- идентификаторы карточек и их URL;
- названия, описания и даты создания карточек;
- текущие списки и архивный статус;
- участников карточек;
- метки карточек;
- даты создания и завершения, если они доступны;
- историю действий с карточками;
- изменения списков;
- изменения участников и меток;
- комментарии и другие события, если они доступны через API и нужны для аналитики.

В первой версии не требуется поддерживать несколько досок, несколько рабочих пространств или произвольное подключение новых досок через интерфейс.

## 3.2. Исторический импорт

Исторические данные — критически важная часть проекта. Без истории переходов между списками нельзя достоверно рассчитывать время выполнения задач за прошлые периоды.

Перед реализацией аналитики необходимо изучить возможности Trello API и провести техническую проверку доступности истории.

Нужно определить:

- насколько глубоко доступна история действий;
- какие типы действий возвращает API;
- есть ли ограничения по пагинации и объёму данных;
- доступны ли действия для архивных карточек;
- как восстанавливать порядок событий;
- какие события позволяют определить переходы между этапами;
- какие данные отсутствуют или не могут быть восстановлены.

Нельзя считать текущий список карточки достоверным источником её прошлого состояния.

### Требования к импорту

1. Выполнять первоначальную загрузку карточек, списков, участников и доступной истории.
2. Сохранять историю действий с исходными идентификаторами Trello.
3. Поддерживать постраничную загрузку.
4. Поддерживать продолжение импорта после остановки или ошибки.
5. Не загружать повторно уже сохранённые события.
6. Обеспечить идемпотентность обработки: повторный запуск не должен создавать дубликаты или искажать статистику.
7. Сохранять прогресс импорта и время последней успешной синхронизации.
8. Показывать пользователю статус и результат импорта.
9. Фиксировать ошибки API, пропущенные данные и ограничения доступа.
10. Предусмотреть ручной повторный запуск синхронизации.

Если API не позволяет восстановить часть истории, приложение должно явно обозначать ограничения. Запрещено подменять отсутствующие данные предположительными датами.

### Контроль качества исторических данных

В интерфейсе администратора показывать:

- дату самого раннего доступного события;
- дату самого позднего импортированного события;
- количество импортированных карточек и действий;
- дату последней успешной синхронизации;
- число ошибок и пропусков;
- статус первоначального импорта;
- периоды и метрики, для которых исторических данных недостаточно.

## 3.3. Регулярная синхронизация

После первоначального импорта приложение должно регулярно получать новые данные.

Требования:

- периодическая фоновая синхронизация;
- возможность ручного запуска;
- повторные попытки при временных ошибках;
- соблюдение ограничений Trello API;
- обработка сетевых ошибок и таймаутов;
- отсутствие дублирования событий;
- логирование результата каждого запуска;
- защита от одновременного выполнения конфликтующих задач синхронизации.

Интервал синхронизации должен задаваться конфигурацией, а не быть жёстко зашит в бизнес-логику.

Приложение должно отображать время последней успешной синхронизации и предупреждать пользователя, если данные устарели.

# 4. Настройка этапов работы

## 4.1. Проблема

В Trello списки могут иметь разные названия и смысл. Для расчёта метрик необходимо определить, какие списки означают начало работы, завершение, ожидание или возврат задачи.

## 4.2. Настройки этапов

Реализовать конфигурацию соответствия списков Trello логическим этапам.

Примеры логических этапов:

- Backlog;
- Ready;
- In Progress;
- Review;
- Testing;
- Blocked;
- Done.

Это примеры, а не обязательный фиксированный workflow. Состав этапов определяется реальной доской.

Администратор или тимлид должен иметь возможность сопоставить список Trello с логическим этапом.

Также необходимо определить:

- какие списки считаются началом выполнения;
- какие списки означают завершение;
- какие списки считаются блокирующими;
- какие переходы означают возврат задачи в работу;
- какие метки обозначают баги;
- какие статусы исключаются из расчёта отдельных метрик.

Если настройки этапов не заполнены, приложение должно предупреждать о невозможности корректного расчёта связанных метрик.

Изменение конфигурации должно сохраняться в БД и отражаться в расчётах. По возможности необходимо сохранять версию конфигурации или время её изменения, чтобы было понятно, по каким правилам рассчитан конкретный отчёт.

# 5. Метрики командной работы

Все метрики должны рассчитываться на основе сохранённой истории событий, а не только текущего состояния карточек.

Для каждой метрики необходимо определить формулу, правила исключения данных, требования к полноте истории и способ отображения в интерфейсе.

## 5.1. Количество закрытых задач

Показывать количество задач, завершённых за выбранный период.

Фильтры:

- период;
- участник;
- тип задачи;
- метка;
- при необходимости — логический этап или категория задачи.

В расчёт входят карточки, которые перешли в настроенный статус завершения в выбранном периоде.

Перемещение уже завершённой карточки между двумя списками завершения не должно приводить к двойному учёту.

Для повторного завершения карточки необходимо определить единое правило: по умолчанию считать уникальные карточки, завершённые за период, а повторные циклы завершения учитывать в отдельной аналитике при наличии достаточной истории.

## 5.2. Throughput — пропускная способность команды

Показывать количество уникальных завершённых задач за день, неделю, месяц или произвольный период.

Поддержать:

- общекомандный показатель;
- показатель по участникам;
- динамику во времени;
- сравнение с предыдущим аналогичным периодом.

Throughput — это количество завершённых задач, а не количество действий в Trello.

Если задача возвращалась в работу и была завершена повторно, правила её учёта должны быть согласованы с метрикой завершённых задач и зафиксированы в документации.

## 5.3. Lead Time

Lead Time — время от момента, когда задача принята в работу по согласованному правилу, до завершения.

Необходимо явно зафиксировать выбранное начало отсчёта. Например, это может быть переход в Ready или момент создания карточки — в зависимости от принятого командой процесса.

В интерфейсе показывать:

- среднее время;
- медиану;
- при необходимости 75-й и 90-й перцентили;
- динамику по периодам;
- список задач с максимальным Lead Time.

## 5.4. Cycle Time

Cycle Time — время от фактического начала выполнения до завершения.

Начало определяется переходом в настроенный этап In Progress или другой согласованный рабочий этап.

Необходимо предусмотреть два варианта представления:

1. **Календарное время** — разница между временными отметками.
2. **Время активного выполнения** — при наличии достоверной модели рабочих этапов и исключаемых периодов.

Нельзя выдавать календарное время за фактическое рабочее время.

## 5.5. Длительность задач

Для каждой карточки рассчитывать доступные временные показатели:

- время от создания до завершения;
- время от начала выполнения до завершения;
- время нахождения на отдельных этапах;
- количество возвратов в работу;
- длительность последнего цикла выполнения;
- длительность текущего незавершённого этапа.

В списке задач предусмотреть сортировку по длительности и фильтр по задачам, которые находятся в работе дольше заданного порога.

Порог длительности должен настраиваться.

## 5.6. Возвраты багов

Возвратом бага считать повторное открытие или возврат в рабочий процесс после того, как карточка уже была переведена в настроенный статус завершения.

В первой версии возвращённым багом считается карточка, соответствующая обоим условиям:

- она классифицирована как баг по настроенной метке или иному явному правилу;
- после завершения она снова перешла в рабочий статус.

Необходимо различать:

- возврат задачи в работу;
- повторное открытие бага;
- повторное завершение бага.

Если карточка была перемещена между статусами Done, но не возвращалась в рабочий процесс, это не должно автоматически считаться возвратом.

### Показатели

- количество возвращённых багов;
- количество багов, которые были завершены за период;
- процент возвратов;
- динамика возвратов;
- список возвращённых багов;
- количество возвратов на одну карточку;
- распределение по участникам и меткам, если данных достаточно.

Формула процента возвратов:

`Количество уникальных багов, возвращённых в работу после завершения / Количество уникальных завершённых багов в той же когорте × 100%`

Для корректного расчёта числитель и знаменатель должны относиться к одной когорте завершённых багов. Если доступные данные не позволяют сформировать сопоставимую когорту, интерфейс должен явно обозначать ограничение.

## 5.7. Время исправления возвращённого бага

Для каждого возвращённого бага рассчитывать время от события повторного открытия или возврата в рабочий процесс до следующего завершения.

Показывать:

- среднее время исправления;
- медиану;
- количество исправленных возвращённых багов;
- список багов, которые ещё не исправлены;
- длительность текущего повторного цикла;
- историю возвратов и повторных завершений.

Для карточек с несколькими возвратами хранить каждый цикл отдельно.

Если событие возврата нельзя однозначно определить из истории Trello, карточка должна попадать в список данных, требующих проверки, а не рассчитываться по предположению.

## 5.8. Незавершённые и зависшие задачи

Показывать:

- количество задач в работе;
- количество задач без движения дольше заданного периода;
- время нахождения в текущем списке;
- задачи с наиболее длительным Cycle Time;
- задачи без назначенного исполнителя;
- задачи, находящиеся в блокирующих статусах.

Отсутствие действий по карточке не всегда означает отсутствие работы. Поэтому такой показатель называется отсутствием активности в Trello, а не доказательством того, что исполнитель не работал.

## 5.9. Распределение задач по участникам

Показывать:

- количество завершённых задач;
- количество активных задач;
- число задач в разных этапах;
- длительность задач;
- участие в исправлении возвращённых багов;
- количество зависших задач.

Учитывать, что у карточки может быть несколько исполнителей. В общекомандной статистике одна карточка учитывается один раз, а в персональной аналитике должна быть явно описана логика распределения карточек между участниками.

Количество задач не является самостоятельной оценкой продуктивности сотрудника. В интерфейсе не следует представлять этот показатель как рейтинг эффективности человека без дополнительного контекста.

# 6. Обзор выполненной работы

## 6.1. Назначение

Создать отдельный раздел для подготовки краткого обзора работы команды за выбранный период.

Основной сценарий — тимлид проводит дейлик или встречу раз в несколько дней и хочет быстро получить список того, что команда сделала, над чем работает и какие проблемы остаются.

## 6.2. Периоды

Предусмотреть готовые варианты:

- сегодня;
- вчера;
- последние 3 дня;
- последние 7 дней;
- текущая неделя;
- предыдущая неделя;
- произвольный период.

Границы периода должны быть однозначными и учитывать часовой пояс приложения.

## 6.3. Состав отчёта

Отчёт должен включать следующие разделы.

**1. Краткая сводка**
- сколько задач завершено;
- сколько багов исправлено;
- сколько задач возвращено в работу;
- сколько задач осталось в работе;
- основные изменения относительно предыдущего периода.

**2. Выполненные задачи**
- название;
- ссылка на Trello;
- исполнители;
- дата завершения;
- тип задачи;
- метки.

**3. Работа над багами**
- новые исправленные баги;
- возвращённые баги;
- повторные исправления;
- баги, которые всё ещё находятся в работе.

**4. Текущая работа**
- незавершённые задачи;
- текущий этап;
- длительность текущего этапа;
- последняя активность;
- блокирующие статусы.

**5. Проблемы и отклонения**
- задачи с высокой длительностью;
- задачи без движения;
- возвраты багов;
- неполные исторические данные;
- проблемы синхронизации, если они влияют на достоверность отчёта.

## 6.4. Требования к отчёту

- Данные берутся из PostgreSQL, а не собираются вручную из Trello при каждом открытии страницы.
- Отчёт можно пересчитать за любой период.
- Для каждой задачи есть ссылка на исходную карточку.
- Отображаются даты и время событий, на которых основан отчёт.
- Можно фильтровать отчёт по участникам и типам задач.
- Доступен просмотр предыдущих периодов.
- Отчёт можно скопировать в буфер обмена в текстовом формате.
- Отчёт можно использовать как основу для сообщения в командный чат.

Автоматическая генерация текста с помощью LLM не является обязательным требованием первой версии. Сначала необходимо реализовать достоверную выборку и расчёт метрик.

Если впоследствии будет добавлена генерация текста ИИ, она должна опираться только на полученные данные и не выдумывать выполненные задачи, причины задержек или результаты команды.

# 7. Интерфейс приложения

## 7.1. Главная страница — Dashboard

Отображать сводные показатели за выбранный период:

- Throughput;
- количество завершённых задач;
- медианный Lead Time;
- медианный Cycle Time;
- процент возвратов багов;
- медианное время исправления возвращённых багов;
- количество активных и зависших задач.

Для каждого показателя предусмотреть краткое пояснение формулы или правила расчёта.

## 7.2. Графики

Минимальный набор:

1. Количество завершённых задач по дням или неделям.
2. Динамика Throughput.
3. Динамика Lead Time и Cycle Time.
4. Динамика возвратов багов.
5. Время исправления возвращённых багов.
6. Распределение задач по этапам.
7. Длительность выполнения задач.
8. Распределение задач по участникам.

Периодичность агрегации должна зависеть от выбранного диапазона. Для коротких периодов использовать дни, для длительных — недели или месяцы.

Таблица задач с колонками:

- название;
- тип;
- исполнители;
- текущий этап;
- дата создания;
- дата начала выполнения;
- дата завершения;
- Lead Time;
- Cycle Time;
- количество возвратов;
- ссылка на Trello.

Функции:

- фильтрация;
- сортировка;
- поиск по названию;
- переход в Trello;
- просмотр истории карточки;
- фильтрация по участнику, метке, этапу и периоду.

Для незавершённых задач показывать текущую длительность вместо даты завершения.

## 7.4. Страница истории карточки

Отображать хронологию событий:

- создание;
- переходы между списками;
- назначения и снятия исполнителей;
- изменения меток;
- завершения;
- возвраты в работу;
- повторные завершения.

Для каждого события показывать время и доступные сведения об авторе.

Если событие не удалось однозначно интерпретировать, оно должно оставаться доступным в сырой истории, но не использоваться в расчётах, для которых оно недостаточно достоверно.

## 7.5. Страница отчётов

- выбор периода;
- выбор участников;
- сводные показатели;
- выполненные задачи;
- баги и возвраты;
- текущие проблемы;
- копирование отчёта;
- отображение качества исторических данных.

Предусмотреть настройки:

- Trello API и идентификатор доски;
- расписание синхронизации;
- соответствие списков логическим этапам;
- метки багов;
- правила начала и завершения задачи;

- часовой пояс;
- управление пользователями и ролями;
- состояние импорта и синхронизации.

Секреты Trello не должны возвращаться в открытом виде при чтении настроек через API.

## 11.1. Архитектурные требования

- Разделять HTTP-слой, бизнес-логику и доступ к данным.

- Использовать контексты Go для запросов и фоновых операций.
- Обрабатывать ошибки явно, не игнорировать их.
- Изолировать работу с Trello API в отдельном модуле.
- Поддерживать отмену и безопасное завершение фоновых задач.
- Предусмотреть таймауты внешних запросов.
- Не допускать повторной параллельной синхронизации одних и тех же данных.
- Использовать транзакции там, где они нужны для целостности данных.
- Разделять конфигурацию и код.
- Поддерживать health check и readiness check.

## 11.2. Фоновая обработка

Синхронизация и тяжёлые пересчёты не должны выполняться внутри пользовательского HTTP-запроса.

Необходимо предусмотреть:

- запуск по расписанию;
- ручной запуск;
- контроль текущего состояния;
- обработку повторных попыток;
- сохранение прогресса;
- журналирование;
- безопасное завершение процесса.

В первой версии отдельный брокер сообщений не требуется, если объём задач и нагрузка позволяют обойтись внутренним планировщиком и механизмами PostgreSQL.

# 13. Локальная разработка через Docker Compose

Docker Compose используется для локального окружения разработчиков и ИИ-агентов. Production-развёртывание через Docker не требуется.

## 13.1. Сервисы

Создать локальное окружение со следующими компонентами:

**PostgreSQL**
- отдельный контейнер;
- постоянный volume;
- health check;
- настройки подключения через переменные окружения.

**Go backend**
- подключение к PostgreSQL по имени Docker-сервиса;
- запуск миграций согласно принятому процессу;
- доступность API на локальном порту;
- удобный режим разработки с перезапуском при изменении кода, если выбранный инструмент это поддерживает.

**Vue frontend**
- запуск dev-сервера;
- доступ к backend API;
- горячее обновление интерфейса.

## 13.2. Конфигурация

Создать:

- `docker-compose.yml`;
- `.env.example`;
- `.gitignore`;
- документацию локального запуска;
- инструкции по миграциям;
- команды запуска тестов.

Файл `.env` исключить из Git. Реальные ключи Trello, пароли и другие секреты не должны храниться в репозитории.

## 13.3. Команды разработчика

Документировать команды для:

- запуска окружения;
- остановки окружения;
- просмотра логов;
- применения миграций;
- запуска unit-тестов;
- запуска integration-тестов;
- пересоздания тестовой БД;
- удаления локальных данных с явным предупреждением.

## 13.4. Критерии готовности локального окружения

- Проект запускается по инструкции на чистом рабочем окружении.
- PostgreSQL сохраняет данные между перезапусками контейнера.
- Backend подключается к БД без ручной настройки внутри контейнера.
- Frontend обращается к API.
- Миграции воспроизводимы.
- Тесты можно запустить документированной командой.
- Секреты не попадают в Git.

# 14. Production-развёртывание на сервере с Nginx

Production-развёртывание выполняется на существующем сервере без обязательного использования Docker Compose.

## 14.1. Frontend

- Собрать Vue-приложение в production-режиме.
- Разместить статические файлы в каталоге, обслуживаемом Nginx.
- Настроить fallback для клиентской маршрутизации Vue Router.
- Не включать секреты backend в frontend build.
- Использовать относительный путь `/api/v1` для API, если приложение и API доступны через один домен.

## 14.2. Backend

- Собрать Go-приложение под ОС и архитектуру сервера.
- Разместить бинарный файл в согласованном системном каталоге.
- Запускать приложение через `systemd`.
- Настроить автоматический запуск после перезагрузки.
- Настроить перезапуск после аварийного завершения.
- Настроить пользователя сервиса с минимально необходимыми правами.
- Хранить конфигурацию и секреты отдельно от репозитория.
- Настроить корректное завершение приложения при остановке сервиса.

## 14.3. Nginx

Настроить:

- раздачу статических файлов frontend;
- проксирование `/api/v1` на Go backend;
- корректную передачу необходимых HTTP-заголовков;
- таймауты для API;
- HTTPS в соответствии с существующей конфигурацией сервера;
- доступность health endpoint только в необходимом объёме.

Не изменять существующие конфигурации Nginx без проверки влияния на другие приложения на сервере.

## 14.4. PostgreSQL

- Использовать отдельную БД и пользователя приложения.
- Выдать минимально необходимые права.
- Хранить данные вне временных каталогов приложения.
- Настроить резервное копирование.
- Документировать восстановление.
- Выполнять миграции контролируемо при обновлении приложения.

## 14.5. Обновление приложения

Документировать процесс:

1. Получение новой версии кода.
2. Проверка тестов.
3. Сборка frontend и backend.
4. Резервное копирование при необходимости.
5. Применение миграций.
6. Обновление файлов.
7. Перезапуск сервиса.
8. Проверка health endpoint и основных пользовательских сценариев.
9. План отката при ошибке.

Миграции должны быть спроектированы с учётом безопасного обновления существующих данных.

## 14.6. Критерии готовности production

- API доступен через настроенный адрес.

# 15. Тестирование

Тесты обязательны для всех основных модулей. Наличие тестов не заменяет ручную проверку интеграции и пользовательских сценариев.

## 15.1. Unit-тесты

Покрыть:

- расчёт Throughput;
- расчёт Lead Time;
- расчёт Cycle Time;
- определение начала и завершения задачи;
- определение возврата бага;
- расчёт времени исправления возвращённого бага;
- обработку нескольких циклов выполнения;
- фильтрацию и агрегацию по периодам;
- обработку неполной истории;
- правила исключения некорректных событий.

Тесты должны включать пограничные случаи, в том числе несколько переходов между статусами, повторные завершения, архивные карточки и отсутствие части событий.

## 15.2. Integration-тесты

Проверить:

- работу с PostgreSQL;
- применение миграций;
- импорт Trello-данных;
- идемпотентность синхронизации;
- восстановление после прерванного импорта;
- работу REST API;
- авторизацию и проверку прав;
- корректность формирования отчётов;
- обработку ошибок внешнего API.

Для тестов использовать отдельную тестовую БД и контролируемые фикстуры.

## 15.3. Frontend-тесты

Проверить:

- отображение метрик;
- работу фильтров;
- обработку ошибок API;
- отображение пустых состояний;
- корректность ссылок на карточки;
- отображение предупреждений о неполных данных;
- разграничение доступных действий по ролям.

## 15.4. Общие требования

- Все новые расчётные функции должны иметь тесты.
- Исправление обнаруженной ошибки должно сопровождаться тестом, воспроизводящим ошибку.
- Нельзя отключать тесты только ради успешного прохождения CI.
- Все тесты должны быть воспроизводимыми.
- Не использовать реальные production-секреты в тестах.
- В документации описать запуск всех видов тестов.

# 19. Нефункциональные требования

## Производительность

- Использовать пагинацию для больших списков.
- Не загружать всю историю карточек в один запрос frontend.
- Тяжёлые расчёты выполнять на backend.
- Использовать индексы PostgreSQL.
- Предусмотреть кэширование или предварительную агрегацию, если реальные объёмы данных потребуют этого.
- Не оптимизировать систему преждевременно без измерений.

## Надёжность

- Ошибка одной синхронизации не должна приводить к потере ранее загруженных данных.
- Импорт должен поддерживать восстановление после прерывания.
- Повторная обработка событий должна быть безопасной.
- Фоновые задачи должны корректно останавливаться при завершении backend.
- Ошибки внешнего API должны быть видны в логах и статусе синхронизации.

## Безопасность

- Все секреты находятся вне исходного кода.
- Доступ к API защищён авторизацией.
- Проверка прав выполняется backend.
- Используется HTTPS в production.
- Пароли хранятся в виде безопасных хешей, если используется собственная авторизация.
- Логи не содержат токены, пароли и чувствительные данные.

## Поддерживаемость

- Бизнес-правила отделены от инфраструктуры.
- Формулы аналитики документированы.
- Схема БД изменяется через миграции.
- Все ключевые сценарии покрыты тестами.
- Изменения выполняются небольшими, проверяемыми этапами.

# 22. Главный принцип реализации

**Сначала достоверные данные и прозрачные формулы, затем визуализация и автоматизация.**

При разработке нельзя считать метрику готовой только потому, что на графике отображается число. Для каждой метрики должны быть понятны источник данных, формула, ограничения истории и правила обработки неоднозначных событий.

Первым этапом следует проверить Trello API и доступность истории. Затем подготовить локальное окружение Docker Compose, модель данных и механизм импорта. После этого последовательно реализовать расчёты, API, интерфейс и production-развёртывание.

Каждый этап завершается тестами, документацией и проверяемыми критериями приёмки.
