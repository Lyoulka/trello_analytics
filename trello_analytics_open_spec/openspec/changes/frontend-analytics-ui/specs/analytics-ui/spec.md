# Spec Delta

## Purpose

Предоставляет Vue 3 интерфейс для входа, просмотра командной аналитики, задач, отчётов и настроек на данных backend API без клиентского пересчёта формул метрик. Визуальное направление — единый аналитический UI для Team Lead на базе референса shadcn/vue (без копирования чужого продукта и без изменения backend-контрактов).

## ADDED Requirements

### Requirement: Авторизация в UI
Интерфейс MUST предоставлять экран входа и учитывать сессию пользователя; неавторизованный доступ к защищённым страницам MUST перенаправляться на login.

#### Scenario: Успешный вход
- **WHEN** пользователь вводит верные учётные данные
- **THEN** UI MUST перейти к Dashboard (или последнему защищённому маршруту)

### Requirement: Единая дизайн-система UI
Frontend MUST использовать один согласованный UI-подход на стеке Vue 3 + TypeScript + Vite: **shadcn-vue + Tailwind CSS** как компонентный и визуальный базис (референс: https://www.shadcn-vue.com/docs/components). MUST NOT подключать параллельно другой полный UI framework. Chart.js + vue-chartjs MAY использоваться только для графиков и MUST визуально согласовываться с токенами той же системы. Dashboard, карточки Trello, отчёты и настройки MUST разделять общую навигацию, палитру, типографику, отступы и паттерны Card / Table / формы.

#### Scenario: Согласованность экранов
- **WHEN** пользователь переходит между Dashboard, Cards, Reports и Settings
- **THEN** shell навигации, плотность отступов, стили кнопок/инпутов/карточек и типографика KPI MUST оставаться визуально согласованными

#### Scenario: Без смешения UI kits
- **WHEN** собирается production frontend
- **THEN** зависимости MUST NOT включать второй полный UI framework наряду с shadcn-vue/Tailwind

### Requirement: Состояния загрузки, пустоты, ошибок и адаптивность
Каждый экран с данными API MUST поддерживать состояния loading, empty и error; интерфейс MUST быть usable на desktop и tablet (адаптивная компоновка shell и основных секций).

#### Scenario: Loading
- **WHEN** запрос к API ещё выполняется
- **THEN** UI MUST показать скелетон или индикатор загрузки вместо пустой области контента

#### Scenario: Empty
- **WHEN** API возвращает успешный ответ без данных для выбранных фильтров
- **THEN** UI MUST показать пустое состояние с кратким объяснением (не маскировать отсутствие данных нулями метрик)

#### Scenario: Error
- **WHEN** запрос к API завершается ошибкой
- **THEN** UI MUST показать понятное сообщение об ошибке без внутренних секретов и стеков

#### Scenario: Tablet layout
- **WHEN** viewport соответствует планшету
- **THEN** навигация и основные блоки MUST оставаться доступными без горизонтального «ломания» ключевых таблиц/фильтров (допустима адаптация: collapse sidebar, stack KPI)

### Requirement: Честность данных и демо-макеты
Рабочие экраны, обращающиеся к `/api/v1`, MUST отображать только значения из ответов API (включая `null`/отсутствие как «нет данных»). UI MUST NOT подставлять выдуманные метрики в рабочие API-вызовы и MUST NOT менять backend-контракты ради отображения. Демонстрационные данные MAY использоваться только в явно обозначенных макетах/превью с видимой пометкой demo/mock.

#### Scenario: Missing metric
- **WHEN** API возвращает `null` или опускает метрику
- **THEN** UI MUST показать состояние «нет данных» / em dash / эквивалент и MUST NOT отображать `0` как будто значение посчитано

#### Scenario: Demo preview
- **WHEN** показывается макет с демонстрационными цифрами до готовности данных
- **THEN** UI MUST явно пометить контент как demo/mock и MUST NOT выдавать его за ответ рабочего API

### Requirement: Dashboard и графики
Dashboard MUST показывать сводные метрики за выбранный период и минимальный набор графиков динамики из ТЗ §7.1–7.2, получая значения только из API.

#### Scenario: Смена периода
- **WHEN** пользователь меняет период
- **THEN** связанные виджеты Dashboard MUST перезапросить данные с новым фильтром

#### Scenario: Нет клиентских формул
- **WHEN** отображается Throughput/Lead/Cycle/reopen
- **THEN** UI MUST NOT пересчитывать формулы локально из сырых events

### Requirement: Карточки и история
UI MUST предоставлять таблицу карточек с фильтрами/сортировкой/поиском, ссылку на Trello и страницу хронологии событий карточки.

#### Scenario: Открытие истории
- **WHEN** пользователь открывает историю карточки
- **THEN** события MUST отображаться хронологически с датами

### Requirement: Отчёты и копирование
Страница отчётов MUST позволять выбрать период/участников, показать секции обзора и скопировать текстовый отчёт в буфер обмена.

#### Scenario: Copy report
- **WHEN** пользователь нажимает копирование
- **THEN** в буфер MUST попасть текстовое представление на основе данных API

### Requirement: Настройки, sync status и warnings
UI MUST показывать настройки workflow (по роли), статус sync/качества данных и предупреждения о неполных данных или незаполненном workflow; нули MUST NOT подменять отсутствующие значения.

#### Scenario: Incomplete history banner
- **WHEN** API возвращает warning о качестве данных
- **THEN** UI MUST показать понятное предупреждение пользователю

#### Scenario: Роль Member
- **WHEN** пользователь Member открывает settings
- **THEN** UI MUST NOT предлагать действия, запрещённые ролью (и API всё равно откажет)
