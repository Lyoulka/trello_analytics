# Design

## Context

Change `spike-trello-history` — блокирующее исследование до аналитического движка. Кодовая база backend/frontend пока без прикладной реализации; OpenSpec store и ТЗ уже есть. Целевой стек: Go backend, Vue 3 frontend, PostgreSQL.

## Goals / Non-Goals

**Goals:**

- Подтвердить empirically, какие данные истории доступны через Trello API для одной доски.
- Зафиксировать ограничения пагинации, глубины, архивных карточек, ошибок и rate limits.
- Подготовить матрицу «событие → метрика» и список пользовательских предупреждений.
- Описать алгоритм идемпотентности и resume для будущего импортера.
- При необходимости создать минимальный throwaway/прототип клиента в `trello_analytics_back` только для исследования.

**Non-Goals:**

- Реализация production sync-сервиса, scheduler, analytics engine, Dashboard.
- Финальная схема БД продукта (достаточно черновых выводов для будущих миграций).
- Изменение production Nginx/systemd.
- Утверждение Lead Time start-rule команды (это OQ после spike).

## Decisions

1. **Исследование read-only.** Только чтение Trello API; никаких изменений доски.
2. **Секреты вне Git.** Key/token через переменные окружения; в отчётах — только обезличенные id/агрегаты.
3. **Документы как основной deliverable.** Обязательный `docs/trello-integration.md`; детальный лог — `docs/trello-history-spike-results.md` при объёме данных.
4. **Прототип опционален, но предпочтителен на Go.** Если создаётся код — минимальный CLI/скрипт в `trello_analytics_back` (например `cmd/trello-spike`), без HTTP API продукта и без формул метрик.
5. **Идемпотентность на уровне id.** Эксперимент проверяет уникальность `id` action и стратегию «insert ignore / upsert by trello_action_id»; полноценная таблица Postgres может быть временной или in-memory set — главное доказать подход.
6. **Никаких выводов «по документации Trello» без прогона.** Официальные docs можно цитировать как гипотезу, факт — только из эксперимента.

## Research plan

### A. Типы событий

Проверить (как минимум) сценарии:

| Сценарий | Ожидаемая польза для метрик |
|----------|-----------------------------|
| createCard | точка отсчёта Lead Time (если выбрано) |
| updateCard (idList) | переходы этапов, start/done, reopen |
| updateCard (closed) | архивация |
| addMemberToCard / removeMemberFromCard | workload / история исполнителей |
| addLabelToCard / removeLabelFromCard | баг-метки |
| commentCard | опционально активность |
| прочие типы, встретившиеся в выборке | не отбрасывать без анализа |

Для каждого: наличие `id`, `date`, `idMemberCreator`, payload list before/after, связь с card id.

### B. Пагинация и глубина

- Запросить actions доски и/или карточек с limit.
- Пройти несколько страниц (before/since или аналог, что вернёт API).
- Зафиксировать самую раннюю и самую позднюю дату.
- Отметить, обрывается ли история раньше создания доски/карточек.

### C. Архивные карточки

- Выбрать архивные карточки.
- Запросить их actions отдельно и/или через board actions.
- Сравнить полноту с неархивными.

### D. Ошибки и лимиты

- Зафиксировать коды 401/403/404/429 и сетевые таймауты (контролируемо).
- Описать рекомендуемую политику retry для будущего sync (без реализации scheduler).

### E. Идемпотентность и resume

- Сохранить набор action id.
- Повторить загрузку той же страницы → пересечение id = 100% ожидаемых дублей.
- Прервать обход страниц, сохранить cursor, продолжить → отсутствие пропусков/дублей в объединении.

### F. Матрица метрик

Заполнить в `docs/trello-integration.md` по факту:

Completed/Throughput, Lead Time, Cycle Time, Bug reopen, Fix time, Stale/WIP, Workload.

## Risks / Trade-offs

| Риск | Влияние | Митигация |
|------|---------|-----------|
| История короче нужного | Метрики за прошлые периоды ограничены | Явные UI-ограничения; не выдумывать даты |
| Неоднозначные actions | Ложные reopen/done | Bucket «needs review» |
| Rate limit при полном обходе | Долгий spike | Ограничить выборку + backoff |
| Прототип «протечёт» в продукт | Техдолг | Пометить spike-код; не строить на нём API |

## Migration Plan

Не применимо к данным продукта. После archive change:

- `trello-integration` capability попадёт в main specs;
- следующие changes (`bootstrap-infra`, `trello-sync`) опираются на документированные ограничения.
